# Latter Studio design guide

This guide is the standard for Latter Studio, the admin panel in the Home Assistant sidebar (authored in modular TypeScript under `frontend_src/` on stock `lit` v3.3.3 + `focusSafe` / `live` / duplicate-key-safe `repeat` in `src/lib/lit.ts`, type-checked with mandatory `tsc --noEmit`, and bundled via stock `esbuild` in `frontend_src/build.mjs` into `custom_components/latter/frontend/latter-studio.js`, a hash-pinned lazy `latter-studio-mdi.js` icon-catalog chunk, deterministic `.gz`/`.br` precompressed siblings, and `custom_components/latter/studio/locales/en.json`). Read it before changing Studio. Every change to Studio follows it. The parts that can be checked automatically are enforced by the project's verification checks, named in brackets below (for example `[STUDIO TOKENS]`).

The [decision log](#decision-log) at the end records the standing choices behind this guide.

---

## 1. Purpose and scope

Studio owns three things:

1. **Latter-only settings**: options that exist only in Latter, such as shared entities, remote control groups, BLE calibration, wallpapers, the App Dock, and each Device's Latter settings.
2. **Cross-device actions**: Device groups, staged batch controls, BLE calibration and adoption, backups.
3. **Health and status**: what a Device is doing now and what needs attention.

Raw per-entity controls stay on Home Assistant's device page. Studio shows only a curated set of a Device's entities, in context, and links to Home Assistant for the rest (**Open in Home Assistant**). Studio never duplicates a Home Assistant screen. Clicking **Configure** on the Latter integration card in Home Assistant opens Studio directly (`config_panel_domain=DOMAIN`, D-060), and Studio operates standalone with zero displays configured for BLE Area presence and sensor fusion (D-060).

## 2. The "real feature" rule

Every control in Studio is wired end to end, or it doesn't ship.

- A control reads a real value and writes it through a real handler that has a real effect (a config entry, a subentry, `.storage/latter.site`, a service call, an entity of the bound Device, or a Protocol v3 payload).
- No placeholders, demo values, "coming soon" sections, or settings that are stored but never read.
- **Unknown renders as `—`.** Never show a made-up value ("Online", "Plugged in", "Connected", a hard-coded version) when the real value is unknown. Battery vs. Power status tiles gate strictly on `capabilities.has_battery` (`Plugged in` on non-battery panels), and Firmware tiles gate on real `update.*` entity state (`—` when unknown; D-003, D-066).
- A payload field the UI doesn't read is removed. A command the UI doesn't call is removed.
- If a feature can't be finished, it's removed from Studio until it can.

## 3. Design tokens

Studio matches Home Assistant's own settings pages. Every visual value comes from a token. Tokens are defined **once**, in the `:host` block of `src/styles/tokens.ts` (which composes `STUDIO_STYLES` across `src/styles/{tokens,layout,cards,controls,data,dialogs}.ts`), and each one reads a Home Assistant theme variable with a fallback. No other rule in any stylesheet contains a font size, a pixel spacing value, or a color literal (`[STUDIO TOKENS]`: zero allowed outside `:host`).

Component rules use CSS **logical properties** (`margin-inline-*`, `padding-inline-*`, `inset-inline-*`, `border-inline-*`, `text-align: start`, plus `:host(:dir(rtl))` directional overrides) so right-to-left locales mirror automatically without horizontal drift (D-061).

Markup carries no inline styles (`[STUDIO INLINE STYLES]`). The one exception is a data-driven custom property, set from data on the element that needs it (`style="--signal-pct: 62%"`, `el.style.setProperty("--swatch-color", color)`), and read by a class rule.

| Toolbar and page title | 20 / 400 | `--studio-font-title` | `--ha-font-size-xl` (hass-subpage toolbar) |
| Card and dialog title | 24 / 400, tracking -0.012em, line height 1.2 | `--studio-font-card-title` | `--ha-card-header-font-size`, `--ha-font-size-2xl` (ha-card header) |

### Colors

Colors come only from Home Assistant theme variables, meeting **WCAG 2.2 AA (`>= 4.5:1`)** text and interactive contrast across light and dark themes (D-061, D-062):

- Surfaces: `--primary-background-color` (page), `--card-background-color` / `--ha-card-background` (cards, dialogs, select and combobox popups), `--secondary-background-color`, `--divider-color`; toolbar `--app-header-background-color`, `--app-header-text-color`, `--sidebar-icon-color`.
- Text: `--primary-text-color`, `--secondary-text-color`, `--disabled-text-color`.
- Accent: `--primary-color`; tints are `rgba(var(--rgb-primary-color), <alpha>)`, never a fixed blue.
- Buttons, as ha-button: accent (main action) `--ha-color-fill-primary-loud-resting` / `--ha-color-on-primary-loud`; filled (secondary) `--ha-color-fill-primary-normal-resting` / `--ha-color-on-primary-normal`; plain (text) `--ha-color-on-primary-normal` with a `--ha-color-fill-primary-quiet-resting` hover; danger `--ha-color-fill-danger-normal-resting` / `--ha-color-on-danger-normal`, and `--ha-color-fill-danger-loud-resting` for a confirmation.
- Chips and active navigation pills: semantic `--ha-color-fill-{primary,success,warning,danger}-normal-resting` paired with `--ha-color-on-{primary,success,warning,danger}-normal` so badge labels maintain `>= 4.5:1` contrast in both light and dark modes (D-061).
- Switch, as ha-switch: off `--ha-color-fill-disabled-quiet-resting` track, `--ha-color-border-neutral-normal` border, `--ha-color-on-neutral-normal` thumb; on `--ha-color-fill-primary-normal-resting` track, `--ha-color-border-primary-loud` border, `--ha-color-on-primary-normal` thumb. The `--ha-switch-*` overrides win.
- Fields: `--ha-color-form-background` (hover `--ha-color-form-background-hover`), `--ha-color-border-neutral-loud`.
- Status: `--success-color`, `--warning-color`, `--error-color`, `--info-color`.

Each of these falls back to the older variable a theme may still set (`--input-fill-color`, `--input-idle-line-color`, `--primary-color`, …), then to a literal.

**Light and dark mode.** Studio sets `color-scheme` from Home Assistant's effective mode (`Boolean(hass.themes?.darkMode)`, reflected as the host's `dark` attribute), so the browser draws native popups (select lists, file and color pickers, scrollbars) in the matching scheme. Select options also get the card background and the primary text color explicitly, because a theme's field fill can be translucent.

Literal colors appear only as token fallbacks inside `:host`. User data (a saved color swatch, a wallpaper thumbnail) is the only exception, and it's set from data, never written in CSS.

## 4. Components

Studio has one implementation of each component. A new pattern is added here first, then built once and reused. Studio builds its own CSS components rather than Home Assistant's internal `ha-*` elements (`ha-card`, `ha-switch`, `ha-select`, `ha-dialog`), with **one explicit render-only carve-out: `<ha-icon>`** is allowed for vector icon glyph rendering (including inside the Shortcut icon picker) with zero shadow-root inspection (D-006, D-062).

- **Card**: header (title and actions on the right) → content → optional footer actions separated by a divider, built by `renderCard()` (`src/components/controls.ts`). A card carries a one-line `.card-subtitle` only when it states a warning, consequence, prerequisite, or multi-Device / System blast radius that the title and controls don't show (D-012, D-024). A card that only lists the Device's own entities (marked `data-entity-card`, such as Sleep & wake and Power & battery) hides when the Device has none of them, as an empty group hides its title.
  ```html
  <div class="card">
    <div class="card-header">
      <div class="card-heading"><h3 class="card-title">…</h3><p class="card-subtitle">…</p></div>
      <div class="card-header-actions">…</div>
    </div>
    <div class="card-content">…</div>
    <div class="card-actions">…</div>
  </div>
  ```
- **Collapsible card**: a native `<details class="card">` whose `<summary>` is the card header. Used for long or advanced content (logs, advanced BLE tuning). Inside a card, a nested collapsible section uses `details.sub-collapsible`.
- **Settings row & range controls**: label and optional description on the interior start, the control on the end; no divider between rows (as ha-settings-row), except between rows stacked in a narrow card. Every Latter option and every curated Device setting goes through `renderSettingsRow()`, `renderSelectRow()`, `renderSwitchRow()`, and `renderRangeRow()` / `renderRangeControl()` (`src/components/controls.ts`), which auto-wire `aria-describedby` (`resolveDescriptionId()`) from the control to `.row-description`. Range sliders update a live `.kv-value` readout and `aria-valuetext` (with unit) on `@input` while committing on `@change`. `.settings-row.stacked` puts a wide control under the label. Multi-slot entity lists (calendars, cameras, remotes, Home Hub domains) use `renderEntitySlotList()`.
- **Searchable entity combobox** (D-062): `renderEntityCombobox()` (`src/components/controls.ts`) provides a reusable WAI-ARIA 1.2 `role="combobox"` (`aria-expanded`, `aria-activedescendant`, ArrowUp/ArrowDown/Home/End/Enter/Escape keyboard navigation, top-80 fuzzy-ranked options across friendly name, Area, and `entity_id` with Area/domain/state chips, and explicit Clear button) that never mutates the committed entity value while typing.
- **Sortable lists & pills** (D-064): `renderSortableList()` and `renderPillList()` (`src/components/controls.ts`) provide pointer drag-and-drop reordering via a `>= 32 px` `≡` `.drag-handle` paired with keyboard-accessible `↑`/`↓` (and `‹`/`›`) move buttons across App Dock, Pinned shortcuts, World clocks, entity slots, and category/tool/game pills—using keyed `repeat()`, `requestAnimationFrame` focus restoration, and polite `aria-live` position announcements.
- **Switch**: one style for every on/off setting, drawn like ha-switch (48 × 24 outlined track, 18 px thumb): `<input type="checkbox" class="switch" role="switch">`.
- **Text field and select**: Home Assistant's filled field: form background, 4 px top corners, a 1 px underline that becomes a 2 px primary line on focus, bound via `focusSafe()` (`src/lib/lit.ts`) so live WebSocket pushes never clobber active typing (D-039, D-062). Native `<select>` keeps its own popup, drawn in Home Assistant's light or dark scheme.
- **Segmented control**: for a small either/or choice that changes the rest of a card (Notifications & announcements: Screen notification or Voice broadcast): `.segmented` with `role="radiogroup"` and `role="radio"` buttons using `aria-checked`.
- **Key/value rows**: `.kv-list` > `.kv-row` (label, value); unknown values show `—`. A row that opens something is a `button.kv-row`.
- **Lists**: `.list-row` (with `.list-row-main` and `.list-row-grow`) for short item lists with actions; `.list-block` for an item with a heading row (`.list-row-head`) and stacked fields (`.stacked-field`, `.field-label`). App Dock rows use non-truncating `.dock-row` rules so app titles and summaries wrap cleanly instead of clipping.
- **Tables**: for lists longer than a few rows: `.table-wrap` > `table.data-table`. Sortable headers are `button.sort-btn` inside a `th` with `aria-sort`. Each row is focusable (`tabindex="0"`) and opens its item on click, Enter or Space.
- **Chips**: one shape, `.chip`, with semantic high-contrast variants `.chip-primary`, `.chip-success`, `.chip-warning`, `.chip-error` (`>= 4.5:1`, no class is neutral). Status dots (`.status-dot`) use the same variants.
- **Empty state**: `<p class="empty-state">` renders a sentence that says what's missing and, where possible, how to add it (for example 0-device **Managed devices** CTAs to **View discovered Devices** and **Configure Area presence**; D-066). Never hidden, except inside an entity-only card, which hides as a whole.
- **Loading state**: `.loading-state`, shown until the first payload arrives and while switching to an unhydrated Device (`store.deviceLoading`); the page is never pre-filled with fake values or stale sibling Device fields. If the first load fails, an `.alert.alert-error` with a Retry button replaces it.
- **Error & offline state**: every failed command shows a sticky/dismissible error toast (`.toast.error`) with the reason, from the one place that sends commands. A persistent problem (a Device health issue, a missing required entity) shows as an inline `.alert` (`.alert-warning`, `.alert-error`) in the card it affects. When a managed display is offline or hibernating, **Device → Overview** renders an `.offline-banner` explaining that saved settings queue in Home Assistant and sync on wake/reconnect, while disabling live Quick actions (D-066).
- **Buttons**: pill-shaped like ha-button. `.btn` plus one variant: `.btn-primary` (accent: the main action), `.btn-secondary` (filled: a tonal primary fill), `.btn-text` (plain), `.btn-danger` (danger fill), `.btn-danger-filled` (loud danger, only inside a confirmation dialog). At most **one primary button per card** (D-009); the page header has no Save button (D-010). Two sizes: regular, and `.btn-compact` (`>= 32 px` touch target) for buttons inside rows. Icon-only buttons are `.btn-icon` (`.btn-icon.danger` for delete) and always have an `aria-label`. Clustered one-tap Device actions at the top of Quick actions use `.quick-action-grid` (`renderQuickActionGrid()`) with tonal `.btn.btn-secondary.quick-action-btn` tiles (icon + Sentence-case action name).
- **Dialogs & confirmations**: native `<dialog class="studio-dialog">`, synchronized with store modal state by `syncStudioDialogs()` (`src/components/dialogs/*`) and `syncDialogElement()`. Esc closes it, focus moves into the dialog on open and returns to the opener on close. All destructive and System-wide mutations route through shared `renderConfirmDialog()` (`src/components/controls.ts`), showing consequence copy, affected Device blast-radius counts, and an inline **Download backup first** button before Restore, Remove, or Reset (`Clear logs` stays instant; D-064).
- **Health**: Studio shows Latter's Home Assistant repairs and nothing else as health: both a Device's Overview and the System's Overview render active Latter repairs as a conditional inline alert banner at the top of the view (hidden when zero issues exist), localized via `localizeRepairIssue()` (`hass.localize`) and linking directly to Home Assistant's Repairs page (and to the affected Device from System Overview). Studio never computes a health warning of its own.
- **Accessibility**: every control has a visible label or an `aria-label` plus automatic `aria-describedby` where row descriptions exist; `<latter-studio>` renders persistent visually-hidden `role="status" aria-live="polite"` and `role="alert" aria-live="assertive"` live regions (quietly announcing inline setting saves and list reorders without noisy visual toasts), promotes `#unified-page-title` to `<h1>` (`tabindex="-1"`), renders sidebar items as `<a href="/latter/...">` links with `aria-current="page"`, and reflects `show-menu` when `narrow || hass.dockedSidebar === "always_hidden"` (D-023, D-062); scope and tab bars expose WAI-ARIA `role="tablist"` and `role="tab"` with `aria-selected` and roving arrow-key focus; toggle pills use `role="group"` with `>= 32 px` targets; the color wheel pairs with a native color input and hex field; animations honor `prefers-reduced-motion`; and danger cards/dialogs convey danger via border and confirm button fill rather than low-contrast red body text.
- **View layout** (D-014): a view is `[wide cards] .columns > .column + .column [wide cards]`. Each `.column` is an independent stack, so cards flow top to bottom in their own column and a short card never leaves a gap beside a tall one. Below 760 px of content width the columns become one (the first column, then the second). Only a card with wide content (a log, a table, a gallery) spans the full width, and it goes first or last in the view. A view's cards are assigned to columns in the template; there is no auto-placing grid.
- **Narrow layouts**: Studio sizes to `100dvh`, `.nav-list` uses a scroll-fade mask, and cards are size containers (`src/styles/layout.ts` and `src/styles/controls.ts`); below 520 px of card width, settings rows and list rows stack (a container query, not a viewport media query), paired with `@media (max-width: 480px)` `.list-row` wrap rules so viewports down to 360 px wide never overflow horizontally (D-023, D-062).

## 5. Navigation

- Two scopes, selected at the top of the sidebar: **Devices** first and the default landing page (the Device list), **System** second (`[STUDIO DEFAULT VIEW]`).
- The URL follows the page, so reload and Back keep it:

  | URL | Page |
  | :--- | :--- |
  | `/latter` or `/latter/devices` | Managed devices list (the default) |
  | `/latter/devices/discovered` | Discovered devices (unbound Latter ESPHome hardware & Bluetooth devices) |
  | `/latter/devices/<subentry_id>` | That Device's Overview |
  | `/latter/devices/<subentry_id>/<page>` | `overview`, `display`, `interface`, `audio`, `power`, `presence`, `tools` |
  | `/latter/system/<page>` | `overview`, `shared`, `photos`, `remotes`, `groups`, `presence`, `tools` |

  Studio writes the URL with `history.pushState` and a `location-changed` event, the way Home Assistant's own panels navigate. An unknown path—including a deleted or unknown `/latter/devices/<unknown_id>` route—redirects cleanly (`history.replaceState`) without firing commands for the missing Device (D-023).
- Clicking **Configure** on the Latter integration card in Home Assistant opens `/latter` directly (`config_panel_domain=DOMAIN`, D-060), and the **Visit** link on a Latter Device's Home Assistant device page opens that Device in Studio (`/latter/devices/<subentry_id>`).
- Studio's entry in Home Assistant's sidebar shows the Latter mark, `latter:logo` (D-017). Studio's own toolbar shows only the title, as Home Assistant's toolbars do.
- The page template starts in the Devices state, so nothing flashes before the first render.
- View names are unqualified within their scope and follow Home Assistant **Sentence case** (D-018, D-041, D-061): on the top-level **Devices** lifecycle pages, the compact sidebar shows **Managed** and **Discovered** while the page `<h1>` shows **Managed devices** and **Discovered devices**. On **Managed devices**, the table renders humanized **Model** labels (`model_label`, D-066) and its card header dynamically reflects the active category filter (**All Devices** by default, or **Roaming Devices**, **Latter displays**, etc.), hiding zero-member Device groups and unused specialty categories unless active (D-048). Individual Device pages use concise single-word labels—**Overview**, **Display**, **Interface**, **Audio**, **Power**, **Presence**, and **Tools** (with a **← Managed** back link)—while System pages are **Overview**, **Shared entities**, **Photos**, **Media & remotes**, **Device groups**, **BLE & Area presence**, and **Tools** (D-020, D-021, D-026, D-041, D-061, D-072). **Managed** carries a count badge for total managed subentries, while **Discovered** displays a count badge strictly when at least one non-ignored unbound Latter ESPHome Device is waiting for adoption (D-041, D-066). On **Discovered devices**, unbound Latter ESPHome hardware supports **Ignore** / **Restore** (`Ignored (<N>)`), and clicking **Adopt** navigates directly to the newly adopted Device's Overview (`adopted_subentry_id`; D-066).
- **View responsibility split** (full per-card field reference in [`docs/studio.md`](studio.md)):
  - **System → Overview**: conditional top **Needs attention** (Repairs) and **Hardware ready to adopt** banners; Column 1 renders high-level live **Status** tiles (**Managed Devices** distinguishing `Sleeping` battery hibernate, `Away` / `Scanning` trackers, unexpected `Offline`, and discharging `<= 20%` `Low battery`; **Area presence**; **People & roaming**; **System release**; **Open Repairs** & **Check firmware updates** footer links); Column 2 promotes **Area deployment** above the fold (roaming rollup plus active Areas with live occupancy, stationed Devices, present/sleeping roaming Devices, remotes, sensors, and BLE coverage chips) (D-051, D-076).
  - **System → Photos** (`/latter/system/photos`, D-072): dedicated full-width **Photo library** card with **Upload photos** (multi-file drag-and-drop & interactive pan/zoom crop staging modal), **Import from Media** (Home Assistant `/media` & mounted NAS folder browser with deduplication and 1-click folder-name collection creation), **New collection**, virtual + user collection filters with inline Rename/Delete, live search, `36`/page pagination, **Select** bulk mode, and click-to-edit **Photo editor & crop** modal.
  - **Device → Overview**: conditional **Needs attention** and **Device is offline or hibernating** banners; Column 1 renders high-level live **Status** tiles (**Area**, **Battery** / **Power** gated on `caps.has_battery`, **Wi-Fi** / **BLE** signal, **Firmware** gated on real `update.*` state, staying in a compact 2×2 grid on mobile via container queries) above **Quick actions** (action tiles disabled when offline + sleep-safe **Do not disturb** + live **Speaker volume**, with **Open in Home Assistant** & **Download backup** in the card footer), while Column 2 opens with **Assignments** (**Device group** with automatic `Custom` state, **Save custom group**, and **Manage groups**, plus **Assigned person** and **Remote control scope** opening the shared **Remote** modal in 1 click) above **Timers & alarms** (live ringing **Dismiss** alert, locally ticked **Active timer** countdown + **Cancel timer**, locally ticked **Stopwatch** elapsed + **Reset stopwatch**, and collapsed-by-default 3-slot 2-way **Alarms**) (D-029, D-048, D-049, D-051, D-053, D-065, D-066, D-077).

## 6. Content rules

- Use Home Assistant and IT terminology: **System**, **Sites**, **Areas**, **Devices**, **Roles**, **Policies**, **Bridges**. Never "household", "fleet", or "room" (`[STUDIO TERMINOLOGY]`).
- No marketing device names or personal equipment brands in labels or logic; Studio branches on hardware-manifest traits.
- **Sentence case & hybrid typed i18n** (D-061, superseding D-011 and D-013): Titles, navigation items, card and dialog headers, settings-row/key-value/field/switch labels, table headers, tabs, segmented options, buttons, select options, chips, toasts, and error messages all use Home Assistant's native **Sentence case**—capitalizing only the first word plus proper names, acronyms, and canonical IT/Home Assistant nouns (**System**, **Sites**, **Areas**, **Devices**, **Roles**, **Policies**, **Bridges**, **Home Assistant**, **ESPHome**, **Music Assistant**, **App Dock**, **Voice Follows Me**, **Repairs**, **BLE**, **Wi-Fi**, **PIN**, **UTC**, **SDK**, **IMU**, **NVS**). All UI strings, `DevicePrefSpec` labels, and wire-option display labels live in typed `frontend_src/src/i18n/en.ts` and `src/i18n/index.ts` (`StudioTranslationKey`, `EN_STRINGS`, `PREF_LABELS`, `PREF_OPTION_LABELS`), mirrored deterministically by `build.mjs` into `custom_components/latter/studio/locales/en.json` and overlaid at runtime from `studio/locales/<lang>.json` (`locale_strings`) via `t()`, `tPrefLabel()`, and `tPrefOption()` when `hass.locale.language !== "en"`. Repair banners localize through `localizeRepairIssue()` (`hass.localize`), Home Assistant entity states format through `formatHaEntityState()` (`hass.formatEntityState`), and labels built from entity names go through `entityLabel()` (Sentence case preserving acronyms and units). Help text is one short sentence that says what the setting does, not how it's built.
- Show entity IDs only where the user picks or inspects an entity.
- Units, numbers, weekdays, and dates follow the user's Home Assistant settings (`hass.locale`—`language`, `number_format`, `time_format`, `date_format`, `time_zone`, `first_weekday`—and `hass.config.unit_system`), while Device-scoped alarm summaries and hour-of-day sliders (`:00`) honor the Device's own **Time format** (`12-Hour (AM/PM)` vs. `24-Hour`) and fall back to `hass.locale.time_format` on System pages (D-069). Times are relative ("2 min ago") where that reads better. Studio formats them with one set of cached `Intl` helpers (`src/utils/format.ts`): `fmtNumber`, `fmtPercent`, `fmtDistance` (feet or meters by the unit system), `fmtAgo`, `fmtDateTime`, `hassFirstWeekday`, `defaultLocaleTimeFormat`, `formatClockHhMm`, and `formatHourSlot`. The backend sends timestamps as UTC ISO 8601 and never formats them.

## 7. Engineering rules

- Studio is a `panel_custom` web component (`require_admin=True`, `embed_iframe=False`, `config_panel_domain=DOMAIN`), authored in modular TypeScript (`frontend_src/src/**/*.ts`) organized by functional domain cohesion across a Tarjan SCC zero-cycle DAG with 4 coarse directory boundaries (`frontend_src/build/guardrails.mjs` over `esbuild` `metafile.inputs`, paired with acyclic backend `studio/{settings_cleaners,state_gates,panel,payload,commands,system_commands,device_commands}.py` verified by `tools/verify_ha.py`) on stock `lit` (`LitElement`, `css`, `html`, `live`, `focusSafe` directive, and duplicate-key-guarded `repeat` in `src/lib/lit.ts`), type-checked with mandatory `tsc --noEmit` (`erasableSyntaxOnly: true`, `verbatimModuleSyntax: true`), tested via pure unit tests (`node --test` in `frontend_src/test/`) plus real Playwright Chromium & `@axe-core/playwright` WCAG 2.2 AA E2E suites (`frontend_src/e2e/`), and bundled deterministically via stock `esbuild` (`frontend_src/build.mjs`, Node 24+, `engines.node >= 24`) into minified `custom_components/latter/frontend/latter-studio.js`, a hash-pinned lazy `latter-studio-mdi.js` chunk (loaded via dynamic `import()` only when the Shortcut icon picker opens while `CURATED_MDI_ICONS` stays synchronous), deterministic `.gz` (`mtime=0`) + `.br` precompressed siblings, `studio/locales/en.json` emitted directly via Node 24 ESM TypeScript import, and `StaticPathConfig(..., cache_headers=True)` (`studio/panel.py`) (D-023, D-024, D-060, D-062, D-078). It exposes **zero `window.*` globals** and **zero inline `onclick="..."` string attributes**, and renders **only the active view** on each update.
- Cross-repo catalogs, preference specs (`device_pref_specs`), world-clock zones (`world_clock_zones`), and Studio action/command sets (`studio_contract`) are generated from `esphome-latter-core/protocol/latter_v3.json` via `tools/gen_protocol.py` into `ha-latter/custom_components/latter/protocol_v3.json` and `frontend_src/src/protocol-schema.ts` (`STUDIO_REV = 44`, `ALLOWED_DEVICE_ACTIONS`, `SYSTEM_WS_COMMANDS`, `DEVICE_WS_COMMANDS`, `WORLD_CLOCK_ZONES_CATALOG`, `DEVICE_PREF_SPECS_CATALOG`) with zero hand-copied duplicates (D-036, D-063, D-072, D-074, D-077).
- Studio talks to Home Assistant through admin-gated `websocket_api` commands (`latter/system/*` and `latter/device/*`, enforced with `15 s` standard and `60 s` import/reset client timeouts), plus Bearer-authenticated multipart wallpaper uploads via `XMLHttpRequest` to `POST /api/latter/wallpaper/upload` (`hass.auth`, streaming up to 15 MB without hitting Home Assistant's 4 MB WebSocket frame limit; `fetch` is never called) (D-025, D-062).
- Every command the UI calls exists in the backend, and every backend command is used by the UI (`[STUDIO COMMANDS]`).
- Mandatory `studio_rev` (`44`) is validated on **all 9** read, subscribe, import/export, reset, and mutation WebSocket endpoints (`studio/{commands,system_commands,device_commands}.py`, returning `"version_mismatch"` on mismatch). When the backend reports a `studio_rev` mismatch after an integration update, Studio halts reconnect timers and displays a dedicated **"Latter Studio was updated — reload page"** action banner (D-023, D-065, D-072, D-074, D-077).
- The websocket type is the scope: `latter/system/*` never acts on the selected Device (a System command that acts on one Device names it in its own payload; uploaded photo deletion uses canonical System `delete_photo`), and `latter/device/*` acts on the Device named by its required `subentry_id`.
- The backend never acts on a client-chosen `entity_id` or `src` that it hasn't validated. Device entity actions are limited to the bound Device's own entities; batch System edits use staged `batch_apply_settings`; camera previews never ship pre-signed in state payloads—instead, Studio calls `mint_camera_preview_url` on demand to mint a `600 s` HMAC-signed `/api/latter/camera/system` snapshot URL (working even on 0-display hubs; D-065); zero-device system wallpaper previews and **Rotate signing key** are signed server-side; and `POST /api/latter/wallpaper/upload` enforces Home Assistant's authenticated admin session (`requires_auth = True` + `hass_user.is_admin`, returning `404` on unknown `subentry_id`).
- Every unauthenticated `GET` Latter HTTP view requires a scoped, expiring HMAC signature (`http/signing.py`, 48 h day-bucketed TTL for Protocol v3 resource URLs and short exact expiry for on-demand streams and `600 s` Studio camera previews), while `POST /api/latter/wallpaper/upload` requires an authenticated admin `Bearer` token (D-025, D-065). Studio never builds or signs a URL itself.
- No Home Assistant frontend internals: no `hass-subpage`, no walking other components' shadow roots, no `localStorage.hassTokens`, no `fetch` with stored tokens.
- Home Assistant's own pages (a device page via **Open in Home Assistant**, Repairs, the Latter integration, logs) open in the same tab with `navigateHaPath()` (the history API and a `location-changed` event, as Home Assistant's panels navigate), so Back returns to Studio. Studio never opens Home Assistant's dialogs or flows itself; it opens the page that has them. System and Device diagnostics downloads use short-lived paths signed by Home Assistant's `auth/sign_path` command.
- Studio uses its own CSS rather than Home Assistant's internal `ha-*` elements (`ha-card`, `ha-switch`, …), which aren't a stable public API; **`<ha-icon>` is the sole allowed Home Assistant custom element** (render-only vector icon display; D-006, D-062).
- Subscription bootstrap, reconnect resync, section hashing, and timer diet (D-023, D-031, D-065): `latter/system/subscribe` responds `{ subscribed: true }` and immediately emits the initial full `type: "state"` event (including `catalog`, `pref_specs`, and `world_clock_zones`, eliminating duplicate startup `get_state` calls), and Studio listens to `hass.connection` `"ready"` to resync automatically after Home Assistant restarts with exponential backoff (`2 s → 5 s → 15 s → 60 s`). Subsequent `type: "state"` pushes omit `catalog`, `pref_specs`, and `world_clock_zones` (unless registry changes) and omit unchanged `discovered_ble_devices`, `system_wallpapers`, `photo_collections`, and `ble_area_signatures` via per-subscription SHA-256 section hashes (`ingestPayload` retains previous slices). `ble_survey_delta` attaches strictly when `survey_subentry_id` is non-empty, filters exclusively to `survey_subentry_id`, and coalesces at `4 Hz` (`250 ms`); `system_log` entries ship only while the Logs view is open; and `LatterCoordinator`'s `1 Hz` timer tick is isolated strictly to `LatterTimerRemainingSensor` while Studio ticks `live.timer_ends_at` and `live.stopwatch_started_at` locally only while `Device → Overview` is open with an active timer or stopwatch.
- Namespaced store controllers, `config_rev` optimistic concurrency, and staged Batch controls (D-010, D-023, D-024, D-062, D-064): `StudioStore` namespaces mutations under `store.entity.*`, `store.groups.*`, and `store.tools.*`, guards Device state ingestion by monotonic request token and `subentry_id`, and serializes saves per scope (`saveChain`) with monotonic `expected_config_rev` (`system_config_rev` / `device_config_rev`, refreshing state and showing a conflict toast on WebSocket `"conflict"`). Inline System and Device settings apply immediately as they change (D-010, announced quietly via the polite `aria-live` status region) with snapshot-isolated Device switching (`(scope, targetSubentryId, dirtyPatch)`), **except `System → Device groups → Batch controls`**, which stages edits in `batchDraft` behind **Apply to N Devices** and **Reset** (D-064).
- Per-Device **Perimeter security policy** (`security_pin_policy`: `auto` | `allow` | `require_pin` | `block`, where `auto` resolves to `require_pin` on stationary panels or when a Home Assistant alarm code is configured, else `allow`) and optional PBKDF2-HMAC-SHA256 Device security PINs (hashed on executor threads, falling back to the System security PIN when unset) are configured in Studio, pushed in Protocol v3 `area_context.security_pin_policy`, and enforced server-side (`services/rpc_security.py` & `protocol_policy.py`) on opening locks, opening garage/gate/door covers, and disarming code-less alarms. Home Assistant `alarm_control_panel` entities that define `code_format` (`alarm_caps`) validate and forward the alarm PIN directly to Home Assistant for arming/disarming as required by the panel (D-023, D-040).
- A change to a Device entity (a select, switch or slider of the bound ESPHome device) shows at once: Studio applies the new state locally, so rows that depend on it appear or hide immediately, and keeps it over incoming payloads until the device reports it (at most 8 s); a failed command puts the old state back. The live subscription pushes when the Device's entities change state. Entity rows re-render from that state, preserve active text focus via `focusSafe()`, and keep keyboard focus on the same control.
- Home Assistant's own Assist satellite selects for a Device (Assistant, Finished Speaking Detection, Wake Word, Wake Word 2) are recognized by their translation key and shown on **Audio** with Latter's voice settings. Home Assistant's Wake Word and Wake Word 2 are the one wake-word control; the firmware has no wake-word select of its own. With Wake word mode Disabled the wake words and their sensitivity hide; the assistant settings stay, because the action button, the Trigger voice assistant button and Home Assistant still start the assistant.

## Decision log

A standing decision stays in force until a new entry supersedes it. Changing one requires a new entry that names the entry it supersedes, explains why, and has the project maintainer's approval. Entries are never edited after they're accepted, except to set their status to "Superseded by D-xxx".

### D-001: Devices is the default view and the first tab
- **Date:** 2026-11-07
- **Decision:** Studio opens on the Device list. The scope switcher shows Devices first and System second.
- **Why:** Most visits are about one Device. System settings change rarely.
- **Alternatives:** System first (the previous layout); remember the last scope (rejected: reloads should be predictable).
- **Status:** Accepted.

### D-002: HA-aligned look, no distinct Studio look
- **Date:** 2026-11-07
- **Decision:** Studio looks like Home Assistant's own settings pages: same fonts, spacing rhythm, and theme colors. The long-term goal is that Studio could live natively inside Home Assistant.
- **Why:** Studio is an admin tool inside Home Assistant. A theme change in Home Assistant should change Studio too.
- **Alternatives:** A distinct Studio style (bigger headers, more whitespace, accent-colored section headers).
- **Status:** Accepted.

### D-003: The real-feature rule
- **Date:** 2026-11-07
- **Decision:** Every control is wired end to end or it doesn't ship; unknown values render as `—` ([section 2](#2-the-real-feature-rule)).
- **Why:** A control that does nothing, or a status that's made up, costs more trust than a missing feature.
- **Alternatives:** Ship placeholders behind "coming soon" labels.
- **Status:** Accepted.

### D-004: "People Tracked" means Devices with an assigned person
- **Date:** 2026-11-07
- **Decision:** The System overview counts Devices that have an assigned person, and the row opens the Device list filtered to them.
- **Why:** The old count was every `person.*` entity in Home Assistant, which says nothing about tracking.
- **Alternatives:** Remove the row.
- **Status:** Accepted.

### D-005: Uploaded wallpapers are private and served by signed URL
- **Date:** 2026-11-07
- **Decision:** Uploads are stored in Latter's private storage (`.storage/latter/wallpapers/<device>/`), never under `/config/www`. They're served only through the signed, expiring Latter wallpaper view. Existing uploads are moved there at startup, and stored references are updated.
- **Why:** Home Assistant serves `/config/www` at `/local/` without authentication. Every other Latter resource uses signed URLs.
- **Alternatives:** Keep `/config/www` (rejected: unauthenticated).
- **Status:** Accepted; moving existing uploads at startup superseded by D-019.

### D-006: Own CSS, not Home Assistant's internal `ha-*` elements
- **Date:** 2026-11-07
- **Decision:** Studio builds its components with its own CSS on Home Assistant theme variables.
- **Why:** `ha-*` elements aren't a public API; they may not be loaded and can change in any release.
- **Alternatives:** Use `ha-card`, `ha-switch`, `ha-select` directly.
- **Status:** Accepted; amended by D-062 (explicit render-only `<ha-icon>` carve-out).

### D-007: One Save per scope
- **Date:** 2026-11-07
- **Decision:** System settings are saved with a System command and Device settings with a Device command. One Save button may save whichever scopes have unsaved changes, but each scope is saved independently and saving one never writes the other.
- **Why:** System pages must work with no Device selected, and a Device save must not overwrite System settings.
- **Alternatives:** One combined save command (the previous design, which needed a selected Device).
- **Status:** Superseded by D-010.

### D-008: One media-handoff setting
- **Date:** 2026-11-07
- **Decision:** A Device has one setting for handing media to the Area it moves into, used for both BLE moves and on-device Area picks.
- **Why:** Two overlapping settings, one of them hidden, made the behavior impossible to predict.
- **Alternatives:** Show both settings with honest labels.
- **Status:** Accepted; implemented 2026-11-07 (the firmware's own switch is gone; the Latter setting `area_handoff` decides for both).

### D-009: One primary button per card
- **Date:** 2026-11-07
- **Decision:** The page header's Save is the view's primary button. A card may have one primary button of its own when its single action is the card's purpose (Download, Restore, Send Notification, Upload Photo, Capture Profile). Every other button in a card is secondary, text or icon.
- **Why:** The rule keeps the main action of each card obvious without turning a page of single-purpose cards into a page of secondary buttons.
- **Alternatives:** One primary button per view (the header Save only; every card action secondary).
- **Status:** Accepted.

### D-010: Every setting applies as it changes
- **Date:** 2026-11-07
- **Decision:** There is no Save button. A switch, select or slider applies when it changes (a slider when it's released); a text or number field commits on Enter or when it loses focus. Changes in quick succession are coalesced into one write of just the changed keys, per scope (System or Device), so a run of clicks doesn't flood Home Assistant or the device payload. A failed write shows the error toast and puts the control back to its saved value. Success toasts appear only when the result isn't visible on the page. System and Device settings are still written by separate commands and never write each other. Supersedes D-007; D-009's one-primary-per-card rule stands, minus its header Save.
- **Why:** It's how Home Assistant's own entity and settings controls behave, and a page that mixes "applies now" with "waits for Save" leaves the user guessing.
- **Alternatives:** Keep one Save button for everything (D-007); mark each card as "applies now" or "needs Save".
- **Status:** Accepted; amended by D-064 (carves staged `Batch controls` out behind explicit **Apply to N Devices** + **Reset**, adds monotonic `config_rev` optimistic concurrency, and replaces visual inline save toasts with polite `aria-live` status announcements).

### D-011: Titles use Title Case
- **Date:** 2026-11-07
- **Decision:** Page and nav names, card titles, section and sub-section titles, and dialog titles capitalize every word except the minor words a, an, the, and, or, of, to, in, on, for, with and &, which stay lowercase unless they're first or last ("Location & BLE", "Announcements & Alerts", "Danger Zone", "Display & Home"). Buttons, row labels, options, help text and toasts stay in sentence case. latter-verify's `[STUDIO TITLE CASE]` check enforces it.
- **Why:** The maintainer's choice: titles read as names and stand apart from the controls under them.
- **Alternatives:** Sentence case for every label, as Home Assistant's own settings pages do (the previous content rule).
- **Status:** Superseded by D-013 and D-061 (Home Assistant native Sentence case).

### D-012: No descriptive subtitles
- **Date:** 2026-11-07
- **Decision:** A title has no "what this section configures" line under it. A card keeps a description only when it carries something critical that the title and the controls don't show: a warning, a consequence or a prerequisite (for example "Not a full backup", "Up to 10 cameras", or how to calibrate). Row descriptions under individual settings are unaffected.
- **Why:** Descriptions that restate the controls add reading without adding information, and they hide the few lines that matter.
- **Alternatives:** A one-line description on every card (the previous card rule).
- **Status:** Accepted; partially superseded by D-024 (scoped `.card-subtitle` on System, multi-Device, security, and gallery cards).

### D-013: Titles and labels use Title Case
- **Date:** 2026-11-08
- **Decision:** Title Case extends from titles to every label: settings-row labels, key/value labels ("Latter Version", "Online Devices", "BLE Area Proxies"), Shared Entities labels ("Entry Lock", "Garage Door", "Robot Vacuum"), field and switch labels, table headers, tabs and segmented options, dialog titles, and buttons ("Add Device", "Open in Home Assistant"). The minor words stay as in D-011, and each part of a hyphenated word is capitalized ("BLE-Tracked Devices"). Body text, descriptions, placeholders, select options, chips, toasts and error messages stay in sentence case. `[STUDIO TITLE CASE]` checks every pattern it can match reliably. Supersedes D-011.
- **Why:** The maintainer's choice: one casing for everything that names a thing on the page, so a label never looks different from the title above it.
- **Alternatives:** Title Case for titles only (D-011).
- **Status:** Superseded by D-061 (Home Assistant native Sentence case and hybrid typed `src/i18n/` localization).

### D-014: Two independent column stacks
- **Date:** 2026-11-08
- **Decision:** Every view lays its cards out in two independent column stacks (`.columns > .column`): cards flow top to bottom within their column, rows are never aligned across columns, so there are no gaps. Below 760 px of content width the two columns become one, first column first. Only cards with wide content (logs, tables, galleries) span the full width, placed first or last in the view. Cards are assigned to a column in the template.
- **Why:** The previous auto-fit grid aligned cards in rows, so a short card beside a tall one left a gap, and some views were one full-width column while others were two.
- **Alternatives:** CSS multi-column (`columns: 2`), which balances automatically but moves cards between columns as content opens and closes; a masonry grid (not yet available in every browser).
- **Status:** Accepted.

### D-015: Home Assistant's component metrics
- **Date:** 2026-11-08
- **Decision:** Studio's components copy the metrics and theme variables of Home Assistant's own components (frontend source, 2026.11): ha-card (24 px regular header, 20/16 padding, `--ha-card-*` border, radius and shadow), ha-settings-row (56 px rows without dividers), ha-input's filled field, ha-button (pill; accent, filled and plain), ha-switch (48 × 24 outlined track), the hass-subpage toolbar (56 px, 20 px regular title, `--app-header-*`), and Home Assistant's light or dark `color-scheme` for native popups. Studio still draws them with its own CSS (D-006); section 3 lists each value and the variable it reads. This carries out D-002.
- **Why:** The maintainer found the light theme usable but not like Home Assistant, and native select popups were unreadable in dark mode. Matching the real components, rather than approximating them, makes a theme change in Home Assistant look right in Studio too.
- **Alternatives:** Keep Studio's earlier compact metrics (16 px card titles, 36 px square-cornered controls, row dividers).
- **Status:** Accepted.

### D-017: The Latter mark is the sidebar icon, not a toolbar logo
- **Date:** 2026-11-08
- **Decision:** Studio's toolbar shows only the title "Latter". ### D-031: Three-Tier Entity & Sleep-Safe Subentry Preferences Architecture (`STUDIO_REV` 6)
- **Date:** 2026-11-12
- **Decision:** Establishes **Latter** as the single source of truth for Device configuration, Device Groups, and Home Assistant automations across three strict tiers (`STUDIO_REV` `5 → 6`, `LATTER_SDK_REV` `2026111203`): (1) **Tier 1 (ESPHome Device)** retains strictly hardware pipes (`assist_satellite` + native wake-word/pipeline selects, `media_player`, `update`), hardware lifecycle (`Restart Device`, diagnostic `Screen Backlight`), and hardware/link diagnostics, retiring `modules/settings_entities.yaml` (`~48` duplicate config entities). (2) **Tier 2 (Latter Device)** exposes a sleep-safe Home Assistant automation surface of up to 11 entities (`device_tracker`, `Current Area`, `BLE Distance`, event-driven `Timer Active`, locally ticked `Timer Remaining`, `Alarm Ringing`, subentry-backed `Power Profile`, `Wake Word Mode`, `Alert Volume`, `Find My Device`, and `Activate Screensaver`), plus the hidden diagnostic `Device Preferences` Protocol v3 sensor (`device_prefs`). (3) **Tier 3 (Studio + Protocol v3 `device_prefs` + `PersistedDevicePrefs` v2 NVS)** stores all 45 Device preferences in the Device subentry (`DEVICE_PREF_SPECS`), synthesizes capability-gated `pref_key` items and live `Speaker Volume` / `device_command` Quick Actions in `_augment_esphome_inspector`, stages edits via debounced `save_device_config` (always editable even while battery Devices hibernate) with client- and server-side `Power Profile` preset cascade, dispatches Quick Actions via the `device_action` WebSocket command (`esphome.<node>_latter_device_command`), syncs **System → Device Groups** baselines atomically on subentries without requiring Devices to be awake, and reconciles offline touchscreen edits on `device_hello` via monotonic per-key `prefs_key_seq` last-writer-wins merge.

- **Status:** Accepted.
